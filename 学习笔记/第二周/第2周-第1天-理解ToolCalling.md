## 复盘问题

### 1. tool calling 和普通 API 调用有什么区别？

普通 API 调用通常是把用户问题发给模型，让模型直接生成自然语言回答。

tool calling 则会额外把工具信息传递给模型，例如有哪些工具可以调用、工具名称是什么、工具能做什么、参数应该长什么样。模型会根据用户问题和工具描述，判断是否需要调用工具。如果需要，它会输出一次工具调用请求，包括工具名和参数。

工具信息通常包括：

- 工具名。
- 工具描述。
- 参数 JSON Schema。
- 必填参数。
- 参数含义说明。

在不考虑模型性能和上下文成本的前提下，也可以补充使用示例或边界示例，帮助模型更好地判断什么时候应该调用工具、什么时候不应该调用工具。不过最核心的仍然是：工具描述要清楚，参数 schema 要准确。

### 2. 为什么说模型没有真的执行工具？

模型只是接收工具列表，并根据工具描述和用户问题，决定要不要调用工具，以及调用哪个工具。它输出的是一次“工具调用请求”，而不是工具执行结果。

例如模型可能输出：

```text
调用 get_weather，参数是 {"city":"北京"}
```

真正执行工具的是 Go 程序。Go 程序拿到模型给出的工具名和参数后，需要判断工具是否存在、参数是否合法，然后再调用本地函数、HTTP API、数据库查询或其他外部能力。

工具执行完成后，Go 程序再把工具结果交回模型，由模型根据工具结果整理最终回答。

所以职责边界是：

```text
模型负责选择工具和生成参数。
Go 程序负责校验参数、执行工具、处理错误和返回工具结果。
```

### 3. 为什么工具参数需要 JSON Schema？

JSON 本身很灵活，可以表达字符串、数字、布尔值、数组、对象以及嵌套结构。但也正因为它灵活，如果没有约束，模型可能输出各种不稳定的参数形状。

JSON Schema 的作用，是给灵活的 JSON 加上一层明确约束，让模型和程序都知道工具参数应该满足什么结构。

它可以说明：

- 需要哪些字段。
- 每个字段是什么类型。
- 哪些字段是必填。
- 字段是否只能取固定值。
- 是否允许额外字段。
- 字段的含义和取值边界。

例如天气工具可以要求 `city` 必须是字符串；计算器工具可以要求 `operation` 只能是 `add`、`subtract`、`multiply`、`divide` 之一。

因此，JSON Schema 的价值不是让 JSON 变得“灵活”，而是让模型输出的工具参数更可预测、更容易被程序解析和校验。

### 4. 为什么 Go 侧还要做参数校验？

即使已经给模型提供了 JSON Schema，Go 侧仍然不能完全相信模型输出。

Go 侧做参数校验，是为了避免模型传错参数导致工具调用失败，也是在建立程序的安全边界。模型可能输出缺失字段、错误类型、非法枚举值、超出业务范围的参数，甚至请求一个不存在的工具。

因此，Go 程序需要在真正执行工具前完成校验：

- 工具名是否存在。
- 参数 JSON 是否能解析。
- 必填字段是否完整。
- 字段类型是否正确。
- 枚举值是否合法。
- 参数是否符合业务规则。
- 工具调用是否可能带来安全风险。

JSON Schema 能帮助模型更稳定地生成参数，但 Go 侧校验负责保证工具执行安全、可控、可调试。

## 今日核心理解

tool calling 的本质不是“模型拥有工具”，而是“模型提出工具调用意图，程序负责执行和兜底”。

可以把完整流程理解为：

```text
用户提出问题
  -> Go 程序把用户问题和工具定义发送给模型
  -> 模型判断是否需要工具
  -> 模型输出工具名和参数
  -> Go 程序校验工具名和参数
  -> Go 程序执行工具
  -> Go 程序把工具结果交回模型
  -> 模型基于工具结果生成最终回答
```

最重要的边界是：

```text
模型负责决策。
Go 负责执行。
Schema 负责约束参数结构。
Go 校验负责兜底安全。
```
