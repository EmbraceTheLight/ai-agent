## 复盘问题

### 1. 普通 LLM 请求和 streaming 请求有什么区别？

普通 LLM 请求会在模型生成全部回答后返回，程序一次性拿到完整回答。streaming 请求则是在模型生成一部分内容后就立即返回这一小段增量内容，程序可以边接收边输出。

从用户体验上看，streaming 会逐词或逐句显示回答，首字响应更快，交互体验更好。但 streaming 不一定让模型更快生成完，它只是更早把已经生成的片段返回给用户。

### 2. 为什么要封装 `LLMClient` 接口？

封装 `LLMClient` 接口，是为了让主流程不直接依赖某一个具体模型供应商或 SDK。

CLI 只依赖自己定义的能力，例如：

```go
Generate
Stream
GenerateWithJsonSchema
```

这样以后如果要兼容其他 AI 模型，例如 DeepSeek、阿里云百炼，或者测试时使用 mock client，只要新的实现满足同一个接口，主流程就不需要大改。

接口封装还能让 LLM 调用细节集中在 `internal/llm` 中，避免 API 调用、streaming 处理、JSON Schema 参数等逻辑散落在 `main` 里。

### 3. structured output 比普通自然语言输出稳定在哪里？

结构化输出可以指定模型返回的具体结构，通常是 JSON。相比普通自然语言回答，结构化输出的字段和类型更确定，更适合程序解析和后续分支处理。

例如当前项目希望模型返回：

```json
{
  "intent": "rag_question",
  "answer": "...",
  "confidence": 0.86
}
```

这样 Go 程序可以用 `encoding/json` 解析成 struct，再根据 `intent` 做后续逻辑。

但结构化输出只提高格式稳定性，不代表业务语义一定正确。例如 JSON Schema 可以限制 `intent` 只能是四种类型之一，但模型分类是否合理，仍然需要 Go 侧校验、测试和后续评估。

### 4. 为什么不能把 API Key 写死在代码里？

API Key 属于隐私和敏感配置，不能写死在代码里。

如果写死在代码中，一方面容易泄露给他人，尤其是一旦提交到 Git 历史中就很难彻底清理；另一方面，如果后续更换 API Key，还需要修改代码甚至重新编译，效率低，可维护性也不好。

更合适的方式是：

- 本地开发使用 `.env`。
- 示例配置使用 `.env.example`。
- 部署时使用系统环境变量、容器环境变量或密钥管理服务。

这样可以让配置和代码解耦，也能降低密钥泄露风险。

### 5. 第 2 周 tool calling 要解决什么问题？

tool calling 主要解决的是：让模型具备“选择工具”的能力，从而扩展 AI 的能力边界。

例如查询今日天气，模型本身并不知道实时天气，也不能真的执行函数。它应该判断需要调用天气工具，并给出工具名和参数，例如：

```text
tool: get_weather
arguments: city=北京
```

真正执行工具的是 Go 程序：

```text
用户问天气
  -> 模型判断需要调用 get_weather
  -> 模型给出参数
  -> Go 程序校验参数
  -> Go 程序调用天气 API 或本地工具
  -> Go 程序把工具结果交回模型
  -> 模型整理成自然语言回答
```

所以 tool calling 的核心边界是：

```text
模型负责选择工具和生成参数。
Go 程序负责校验参数、执行工具、处理错误和控制安全边界。
```

这也是为什么工具参数需要 JSON Schema，Go 侧还必须做参数校验，并且 Agent Loop 要设置最大调用次数和超时。

## 本周最重要的理解

第 1 周最重要的收获是：LLM 不应该只被当作一个随便调用的 HTTP 接口，而应该被当作一个需要封装、配置、错误处理和验证的外部服务。

几个关键边界：

- 模型负责生成内容，程序负责控制流程。
- 模型可以输出结构化数据，但程序仍要解析和校验。
- streaming 改善交互体验，但需要处理增量输出。
- API Key 是配置和秘密，不应该写进代码。
- 接口封装是后续 tool calling、RAG、MCP 和 Agent Loop 的基础。
