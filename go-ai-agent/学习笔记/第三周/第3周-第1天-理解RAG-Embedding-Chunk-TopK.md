# 第 3 周第 1 天：理解 RAG、Embedding、Chunk 和 TopK

日期：2026-08-17

## 今日目标

今天的目标是理解 RAG 文档问答的完整流程，并弄清楚 embedding、chunk、向量检索和 topK 分别解决什么问题。

本周开始进入 RAG。相比第 2 周 Tool Calling 让模型“决定调用工具”，RAG 的重点是让模型“基于给定资料回答问题”，并尽量给出可追溯的引用来源。

## 我对 RAG 流程的理解

RAG 可以分成两个阶段：离线预处理阶段和在线查询阶段。

### 离线预处理阶段

```text
原始文档资料
-> 文档解析 / 清洗
-> chunk 切分
-> 为每个 chunk 生成 embedding
-> 将 chunk、embedding 和 metadata 存入向量数据库或向量存储
```

这个阶段的目标是把原始文档变成可检索的知识片段。模型并不会真正“记住”这些文档，而是由程序提前把文档处理成后续能检索的形式。

### 在线查询阶段

```text
用户提出问题
-> 为问题生成 embedding
-> 到向量存储中做相似度检索
-> 取相似度最高的 topK 个 chunk
-> 将这些 chunk 作为上下文，连同用户问题一起发送给 LLM
-> LLM 基于检索出的上下文回答问题
-> 返回答案和引用来源
```

这里检索出来的更准确说是 topK 个 `chunk`，而不是 topK 个完整文档。一个文档可能命中多个 chunk，也可能完全没有命中。

## RAG 的核心理解

RAG 的目标不是让模型拥有知识库，而是在回答前临时检索出相关资料，让模型基于这些资料回答。

可以概括为：

```text
RAG = 检索相关资料 + 让模型基于资料回答
```

它解决的是普通 LLM 的两个问题：

- 模型本身不知道私有文档中的内容。
- 模型可能在没有依据时编造答案。

RAG 通过把相关 chunk 放进 prompt，为模型提供可引用、可检查的上下文。

## 为什么不能整篇文档 embedding

整篇文档 embedding 可以理解为“把整篇文档当成一个超大 chunk”。这样会带来几个问题。

第一，文档过长时，如果命中这篇文档，就可能需要把整篇文档作为上下文放进 prompt，容易占满 LLM 的上下文窗口。

第二，长文档中通常包含多个主题。整篇文档生成一个 embedding 后，语义会变得很宽泛，容易被“平均化”，导致检索结果不够精准。

第三，整篇文档中可能只有一小段和问题相关。如果把整篇文档都交给模型，会引入大量无关信息，影响回答质量。

因此，更合理的方式是将文档切成 chunk，再分别生成 embedding。

## Chunk 太大或太小的问题

### Chunk 太大

chunk 太大会带来两个主要问题：

```text
检索不精准：一个 chunk 中混入多个主题
生成受干扰：放入 prompt 后携带大量无关信息
```

如果 chunk 太大，即使它和问题有一点相关，也可能包含很多不相关内容。模型在回答时会被这些冗余信息干扰。

### Chunk 太小

chunk 太小会导致上下文不足。

例如，一个 chunk 只包含一句话，可能命中了关键词，但缺少定义、条件、主体或上下文。模型虽然拿到了相关片段，却不一定能从中得到完整答案。

所以 chunk 的目标不是越小越好，也不是越大越好，而是要在“检索精准”和“上下文完整”之间取得平衡。

## TopK 太大或太小的问题

topK 表示一次检索返回最相似的前 K 个 chunk。

### TopK 太大

topK 太大会引入更多弱相关甚至无关 chunk。

问题包括：

- prompt 被无关资料占用。
- 模型可能被噪声干扰。
- 多个 chunk 内容冲突时，模型可能选错依据。
- 成本和延迟增加。

### TopK 太小

topK 太小可能导致上下文不够。

有些问题的答案可能分散在多个 chunk 中。如果只取一个 chunk，可能漏掉关键条件或补充信息，导致回答不完整。

因此，topK 也需要通过实际问题和效果对比来调整。

## 为什么回答必须带引用

引用的价值是让回答变得可检查、可追溯。

如果模型回答中带有来源，用户就可以判断：

- 这句话是否真的来自资料。
- 引用是否和问题相关。
- 模型是否误解或歪曲了资料。
- 回答是否出现了幻觉。

RAG 不应该只是让模型“看起来更懂”，而应该让回答有依据。

## 检索结果不相关时怎么办

如果 topK 结果和用户问题不相关，RAG 第一版应该优先拒答，而不是强行回答。

更合适的策略是：

```text
当前资料中没有找到相关信息，因此无法基于已有资料回答。
```

后续可以扩展 web 搜索、`http_get` 或其他外部检索工具作为兜底，但必须清楚区分：

- 答案来自本地知识库。
- 答案来自外部搜索。

否则会破坏 RAG 的可信边界。

## 初步数据结构理解

后续实现时，可以先围绕几个核心结构展开。

```text
Document
```

表示原始文档，应该包含文档 ID、文件路径、标题和原始内容。

```text
Chunk
```

表示切分后的片段，应该包含 chunk ID、所属文档、chunk index、内容和 metadata。

```text
Embedding
```

表示文本对应的向量。后续需要记录向量维度，但不应该在日志中打印完整向量。

```text
SearchResult
```

表示检索结果，应该包含 chunk、相似度分数和来源信息。

## 今日核心理解

今天最重要的理解是：RAG 的关键不是“多塞资料”，而是用合适的 chunk 和 topK，把足够相关、足够可引用的资料交给模型。

如果资料足够相关，模型应该基于资料回答并给出引用；如果资料不足或不相关，模型应该拒答，而不是凭空编造。

可以总结为：

```text
RAG 的价值 = 相关检索 + 基于资料回答 + 引用可追溯 + 无资料时拒答
```
