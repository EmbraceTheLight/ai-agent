## 参数对比

### 1. `chunkSize` 对比

测试问题：

```text
第四周我做了什么
```

固定参数：

```text
topK=5
```

#### `chunkSize=300, overlap=50`

检索结果覆盖了周三、周四、待办事项、周二和周五，召回的日期范围较广。

但由于 chunk 较小，相关内容可能分散在不同片段中。最终回答能够总结主要工作，但部分日期的上下文不够完整，对周一和周五的记录也只能给出资料不足的判断。

小 chunk 的特点是定位更细，但完整上下文更容易被切开。对于需要总结多个日期的大范围问题，较小 chunk 可能需要更大的 `topK` 才能覆盖足够信息。

#### `chunkSize=500, overlap=100`

回答能够覆盖：

- 测试用例修复；
- 编译前端的未识别符号问题；
- 组件展开和平坦化流程；
- Dymola 模型库加密与授权；
- 算法题；
- 周五的平坦化学习。

这组参数在上下文完整性、检索精度和噪声之间取得了较好的平衡，适合作为当前 Demo 的默认配置。

#### `chunkSize=800, overlap=150`

单个 chunk 包含的上下文更多，回答能够补充 `aliasPath`、`targetPath`、实例化组件和平坦化流程等细节。

但是，上下文变大后，回答也更容易把待办事项、已完成事项和遗留问题放在一起。例如，待办事项中标记完成的模型问题被模型直接归入第四周完成的工作，说明大 chunk 会增加状态混淆风险。

### 2. `overlap` 对比

测试问题：

```text
加密授权模型库是怎么操作的
```

固定参数：

```text
chunkSize=500
topK=5
```

#### `overlap=0`

即使没有重叠，检索仍然能够找到加密授权文档中的多个相关 chunk，并还原出设置可见性、保存 `.moe` 文件、创建授权文件、放置授权文件和验证等主要步骤。

这说明对于结构清晰、步骤边界明确的文档，`overlap=0` 也可以正常工作。

#### `overlap=100`

回答中进一步保留了获取 `host-id` 的步骤：

```text
Tools -> License Setup -> Details -> Local host id -> Flexnet
```

适当的 overlap 有助于保留跨 chunk 边界的关联信息，减少一个完整步骤被切分到两个片段后无法同时召回的情况。

#### `overlap=200`

回答同样比较完整，并且能够保留 host-id、授权文件位置和重新加载验证等信息。

不过，较大的 overlap 会使相邻 chunk 的内容重复更多，增加 embedding 计算量和 prompt 中的重复上下文。本次实验没有观察到 `overlap=200` 相比 `overlap=100` 带来明显的回答质量提升。

## `topK` 对比

测试问题：

```text
第四周我做了什么
```

#### `topK=3`

主要命中周三、周四和待办事项。回答能够总结部分工作，但无法覆盖整周的所有日期，适合单日或单主题问题，不适合范围较大的周总结。

#### `topK=20`

额外召回了周五、周二、周一以及加密授权和前端平坦化专题文档，最终回答更加完整，能够补充前端平坦化学习和更多算法题记录。

但是，较大的 `topK` 也带来了更多待办事项、专题资料和低相关片段。上下文越多，模型混淆“已完成”和“待办中”事项的风险越高。

因此，`topK` 的取值需要结合问题范围：

```text
单日 / 单主题问题：topK=3~5
跨日期 / 周总结问题：topK=10~20，并配合过滤或重排序
```

## Demo 人工评估

本周使用固定的第四周工作笔记完成了以下场景验证：

| 场景 | 结果 | 主要观察 |
| --- | --- | --- |
| 只执行 load、chunk、embed | 通过 | 文档能够读取，chunk 和 embedding 能够生成 |
| 查询某一天做了什么 | 基本通过 | 能回答问题，但相似度最高的 chunk 不一定来自目标日期 |
| 查询当周待办事项 | 基本通过 | 能找到待办文档，但需要区分已完成、进行中和待办状态 |
| 查询资料中不存在的 PostgreSQL 持久化 | 通过 | 能明确说明资料中没有证据，未强行编造结论 |
| 查询整周完成的工作 | 通过但受参数影响 | topK 较小时容易漏掉其他日期，扩大召回范围后回答更完整 |
| 查询加密授权模型库操作流程 | 通过 | overlap 对跨步骤信息的保留有帮助，但较大 overlap 会增加重复内容 |

这里的“通过”是指 Demo 能够产生基本符合资料的回答，并不代表检索已经达到生产级准确率。人工评估还需要继续扩展为固定的自动化评测集。

## 本周核心理解

### 1. RAG 的完整流程

```text
本地文档
  -> loader
  -> chunk
  -> embedding
  -> 内存向量库
  -> query embedding
  -> cosine similarity
  -> topK 检索
  -> prompt 拼接
  -> LLM 基于资料回答
  -> 返回引用
```

RAG 的重点不是把所有文档一次性放入 prompt，而是先检索与问题最相关的片段，再让模型基于这些片段回答。

### 2. 检索质量决定回答上限

如果正确资料没有被召回，即使 Prompt 约束写得很好，模型也无法可靠回答。因此 chunk 大小、overlap、topK 和文档覆盖范围都会影响最终结果。

### 3. 引用是回答可信度的一部分

回答中包含源文件和 chunk 索引，可以追溯答案依据，也便于发现模型是否引用了错误资料。引用不能只作为展示信息，还应当参与回答质量评估。

### 4. 拒答是 RAG 的必要能力

当资料中没有 PostgreSQL 持久化记录时，系统能够回答“没有证据表明做过”，而不是根据“后端部署”等相似内容推断已经完成。这是当前 Prompt 约束有效的表现。

### 5. 参数没有脱离数据集的绝对最优值

本次实验中，`chunkSize=500`、`overlap=100` 的综合表现较平衡，但结论只适用于当前文档和问题集合。更长的技术文档、结构化步骤文档或跨文档总结问题，可能需要不同参数。

## 当前不足

- 当前仍然使用内存向量库，每次运行都要重新生成 embedding。
- 还没有持久化向量存储和增量索引能力。
- 还没有 metadata filter，不能先限定日期、目录或文档类型。
- 相似度分数暂时没有设置最低阈值，低相关结果也可能进入 topK。
- 还没有自动区分已完成事项、进行中事项和待办事项。
- 周总结问题可能需要先按文档或日期聚合，再进行回答。
- 当前评估主要是人工观察，还没有自动化的 precision、recall 或 groundedness 指标。
- 不同 chunk 参数产生的候选集合不同，相似度分数不能单独作为效果好坏的判断依据。
