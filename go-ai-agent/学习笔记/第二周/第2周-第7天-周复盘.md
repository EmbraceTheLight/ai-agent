## 本周最重要的理解

本周最重要的理解是：Tool Calling 不是模型真的执行工具，而是模型提出“我要调用什么工具、参数是什么”，真正执行动作的是 Go 程序。

完整链路是：

```text
用户提出问题
模型判断是否需要工具
模型输出工具名和参数
Go 校验参数
Executor 查找并执行工具
Go 将工具结果放回上下文
模型基于工具结果继续决策或生成最终回答
```

因此，Agent 的可靠性不只取决于模型，还取决于程序是否维护好这些边界：

```text
工具定义是否清晰
参数 schema 是否准确
Go 侧校验是否完整
工具是否有安全限制
上下文 history 是否闭环
循环是否有最大步数
错误是否能安全收口
```

## Chat Completions 的收获

本周最重要的工程转折是：从 OpenAI Responses API 的上下文状态问题，转向 Groq Chat Completions。

Responses API 的工具调用上下文更细：

```text
reasoning
function_call
function_call_output
PreviousResponseID
Store
```

但第三方中转站对这些状态机制的支持不稳定，导致模型在第二轮可能遗忘原始任务或工具结果。

Chat Completions 的上下文更直接：

```text
system
user
assistant(tool_calls)
tool(tool_call_id, result)
assistant
```

由 Go 维护完整 `messages` history 后，模型可以稳定看到：

- 原始用户任务。
- 它上一轮请求过哪些工具。
- 每个工具调用对应的结果。
- 当前任务是否还需要继续调用工具。

这让 Tool Call Loop 的状态更加可观察，也更适合当前学习阶段。

## 本周验证结果

### 单工具调用

已验证：

```text
查询广州当前时间
调用 time
模型基于结果回答
```

### 多工具调用

测试问题：

```text
请告诉我现在广州和洛杉矶的时间, 并调用工具告诉我 4*5 的结果是多少
```

观察到的调用链：

```text

```

这说明当前 Tool Call Loop 已经支持连续工具调用和跨工具调用。

### 不需要工具的问题

已验证：

```text
普通概念问题可以直接回答
不会触发工具调用
```

这说明 `ToolChoice=auto` 下模型能够根据任务需要决定是否调用工具。

### http_get 安全边界

已验证：

```text
allowlist 内 URL -> 可以访问
allowlist 外 URL -> 被拒绝
```

同时，`http_get` 单元测试覆盖了 query、header、method、allowlist 和响应体大小限制。

## 错误处理策略

当前阶段采用的策略是：

```text
工具执行失败
FunctionCall 直接返回 error
用户侧只看到通用错误
后台记录具体错误信息
```

这样做是为了避免把敏感信息暴露给用户，例如：

```text
API key
请求 header
内部路径
完整上游响应
stack trace
```

后续可以把工具错误转换为脱敏后的结构化结果，再回传给模型生成友好的最终回答。

例如：

```json
{
  "ok": false,
  "error_code": "divide_by_zero",
  "message": "除数不能为 0"
}
```

## 还不稳定的地方

- Groq 当前只重点验证了 `FunctionCall`，普通输出、流式输出和 JSON Schema 输出仍然沿用 Responses API 风格。
- CLI 后续最好增加 provider 参数，避免不同模型服务的协议差异混在一起。
- 真实模型工具选择具有不确定性，稳定验证 Agent Loop 仍需要 mock 响应测试。
- `output_schema_test.go` 仍需要补充执行和断言。
- `time` 工具返回 JSON 字符串后，需要确保相关测试与新格式一致。
- 工具错误目前直接结束 Agent Run，后续可以支持安全错误回传模型。
- trace 目前还比较临时，后续可以整理为统一结构化日志。

## 第 3 周 RAG 前需要准备什么

第 3 周进入 RAG 前，需要保留第 2 周建立的几个边界意识：

- 模型不能直接访问外部世界，必须通过 Go 控制工具和数据源。
- 所有外部输入都需要校验。
- 所有外部访问都需要边界，例如 allowlist、timeout、大小限制。
- 上下文需要由程序显式维护，不能假设服务端一定保存状态。
- 测试不能完全依赖真实模型，需要引入 mock 或固定样例。

RAG 会把“工具安全边界”扩展到“知识库检索边界”。需要重点关注：

```text
文档如何切分
向量如何生成
检索结果如何进入上下文
如何避免把无关资料塞给模型
如何评估回答是否基于检索内容
```
