新增及调整后的测试覆盖：

- 数组中的嵌套目录保持独立；全部显式根节点自身仍禁止正文修改和删除。
- 同一目录中，一篇笔记持锁时，另一篇笔记的完整追加业务仍可成功。
- 不同克隆位置和写入范围配置不能绕过同一 noteId 的锁；范围外父级路径仍拒绝。
- 两个独立进程共享状态目录时，同一 noteId 互斥、不同 noteId 可继续取得锁，等待可取消。
- 稳定的并发模拟：暂停创建子笔记，竞争的父笔记删除等待至取消；创建完成后，父笔记因不是叶子而拒绝删除。
- 反向并发模拟：暂停叶子删除，竞争的子笔记创建等待至取消；删除完成后，创建发现父笔记不存在，不发送创建请求。
- 操作 ID 独立互斥；旧单 ID 与等价单元素数组记录兼容；数组顺序和重复项不影响重试。
- MCP 协议返回未合并的嵌套数组；多目录新建和搜索要求显式选目标，显式创建、删除及单目录默认行为正常。

原有摘要冲突、快照、未知结果重试、叶子删除、祖先 404 不得误判删除完成及 stdio 子进程测试继续通过。模拟 API 使用假 Token，不访问真实笔记库。

## 真实只读验证

通过新程序的 stdio MCP 连接 TriliumNext 0.104.1。先精确查询确认唯一 `root/temp`，然后选择其一个现有直接子笔记，在临时进程环境中传入包含重复项的嵌套数组。`trilium_info` 返回服务版本 0.3.0，`writeRootIds` 和 `configuredWriteRootIds` 均为 `["v2YidQTHkFIY", "zYNgSdXFYpPF"]`，未合并，旧单值字段为空。

真实验证没有创建、更新或删除笔记，没有改写 `.env` 或 Codex 配置；并发写入及删除竞争通过模拟 API 验证，没有在真实库中制造竞争。

升级时先完成旧版待核对操作、停止旧写入进程，再切换 `bin/trilium-mcp-note-locks.exe` 或重新构建原程序。0.2.0 合并过嵌套数组的操作指纹可能与新版不同，详情及锁协议限制见 [MCP 说明](mcp-guide.md)。
